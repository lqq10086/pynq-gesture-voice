适用场景：派活前、分工前、复查前、交接前。用户说"把这个任务交待给 XX""帮我写个任务书""让另一个 agent 做这块""复核一下这个设计"时使用。


# 任务书模板

七个模板，每个解决一种"讲不清导致的返工"。模板只规定**怎么说清任务**，不规定设计怎么做，
所以换题目、换板卡、换模型都能用。

## 用法

1. 打开对应模板，把方括号里的内容换成你的项目信息。方括号留着不填，模板等于没用。
2. 一个模板整段发给 agent，不要只发其中一段：模板里的约束互相支撑，删一条通常会退化。
   但不要一次把多个模板拼给同一个 agent——04 明确要求"不许改代码"，01 要求"改实现到用例通过"，
   同时发就等于让它自己挑一条执行。先后关系见下。
3. 收到回复后按模板末尾的"验收标准"逐条核对，不满足就退回，不要自己补脑。
4. 如果 agent 三次都做不对，问题通常在模板里某条约束太抽象，把那条改成可核对的动作。

## 几个模板的先后关系

| 场景 | 顺序 | 理由 |
| --- | --- | --- |
| 两拨人分头写硬件与主机 | 02 → 01 | 契约没定就派实现，两边会各自发明接口 |
| 已经从报告定位到要改什么 | 04 → 01 | 04 只许诊断，把"改哪里、判据、回退"写进 01 再动手 |
| 板端现象说不清 | 06 → 01 | 06 只做分层与对照实验，锁定层之后才派修改 |
| 交付前的最后检查 | 05 → 07 | 05 只读复核，07 收口成交接包 |

两次派活之间要保留中间产物：04 的候选清单、06 的实验记录都是 01 的输入，丢掉就得重做一遍诊断。

## 七个模板

| 编号 | 文件 | 解决什么 | 最关键的约束 |
| --- | --- | --- | --- |
| 01 | `prompts/01-task-dispatch.md` | 把任务、白名单、契约、验收、交付位置一次讲清 | 只允许修改的文件必须逐个列出 |
| 02 | `prompts/02-interface-contract.md` | 产出带出处的主机侧与硬件侧共用契约 | 每个数字都要能指回源文件与行号 |
| 03 | `prompts/03-hardware-software-partition.md` | 先算带宽与延迟，再决定谁放哪 | 三种归属都要给数字，不只给推荐 |
| 04 | `prompts/04-bottleneck-from-reports.md` | 从报告里定位瓶颈，产出带成本与回退的候选 | 第一段不许出现"因为所以" |
| 05 | `prompts/05-readonly-review.md` | 只读复核，固定结论格式与证据缺口 | 不得运行、不得改文件、必须写行号 |
| 06 | `prompts/06-onboard-diagnosis.md` | 把板端现象拆成层，用控制实验定位 | 探针必须先证明自己无害 |
| 07 | `prompts/07-handoff-reproduce.md` | 交接包与复现说明，含证据分层 | 未做的一律写 NOT_RUN |

## 选哪个

| 你现在的处境 | 用哪个 |
| --- | --- |
| 要派一件有边界的活给 agent 写代码 | 01 |
| 硬件侧与主机侧由两个 agent 分别写，怕接口对不上 | 02（先）+ 01（后） |
| 算法有了，还没决定哪段放 PS、哪段放 PL | 03 |
| 综合或实现跑完了，要判断下一步改哪里 | 04 |
| 要第二个人看一眼设计或报告，但不许它改东西 | 05 |
| 板子上出现怪现象，说不清哪一层的问题 | 06 |
| 要交给别人接手，或要写复现说明 | 07 |

## 模板为什么这么写

- **只读就是只读**：允许它跑一次综合，报告里就会混进新构建的数字，旧报告立刻不可比。
- **证据分层**：仿真通过、实现通过、板端跑通是三件事，模板要求分别写，不允许合成"验证通过"。
- **失败要留**：被否决的方案、失败的构建、NOT_RUN 的项都是判断依据，删掉就只剩故事。

## 边界

- 模板不提供设计答案，只让 agent 不跑偏，不保证它跑得快。
- 模板不替代契约与报告本身：01 引用 02 的契约，02 的契约要单独维护。
- 嵌赛等正式提交场合要求目录与文件名用英文；模板里的中文只出现在正文。
