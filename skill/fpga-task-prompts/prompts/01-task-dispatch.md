# 01 任务派发提示词

## 什么时候用

要给一个没有历史记忆的 agent 派一件有明确边界的活时用这一条。典型场景：

- 把一段 RTL、一个 HLS 函数、一段 PYNQ 主机侧代码交给子 agent 实现。
- 把一项只读审查交给另一个 agent（这时改用 05 复核提示词）。
- 你已经知道要什么，但担心 agent 顺手改别的文件、改基线、或声称做到了其实没做。

不适合：连目标都还没想清楚的时候。先自己写清一句话目标，再来填这张表。

## 提示词模板

把方括号里的内容替换掉，整段直接发给 agent。

```text
任务：[一句话说明要交付什么，动词开头]

工作目录：[绝对路径]
只允许修改的文件：[逐个列出绝对路径或相对路径，其它一律只读]

先读这些，再动手：
1. [必读文件 1，说明为什么要读它]
2. [必读文件 2]
3. [相关历史报告或日志]

硬性约束：
- 不新建子 agent，不并行改文件。
- 不改动受保护文件：[逐个列出不能修改的基线、构建脚本、测试或文档]；需要修改的测试文件须列入上方白名单，且不得列为受保护文件。
- 不安装依赖，不联网下载。可用工具：[列出已装好的工具与绝对路径]
- 板卡不在手上时：只做离线部分，所有需要上板的项一律写 NOT_RUN，不要用估算值代替实测。
- 不确定的地方先在回复里问，不要猜着写。

接口契约（必须逐字遵守）：
[寄存器表、端口列表、函数签名、文件格式。没有契约就写"无契约，按现有代码风格" ]

完成顺序（按这个顺序做，不要跳）：
0. 先拿到接口契约的草案。红灯用例要写清触发条件与观测点：寄存器接口写地址与偏移，
   流接口写激励帧与期望帧，函数接口写输入与期望返回。没有契约就只能先写一条探身份的用例
   （读版本寄存器、发一条最小合法帧、调一次空输入），不要自己发明地址或帧格式。
   契约未定时，第 1 步允许只写"能运行并失败"的最小用例。
1. 先写失败用例，运行它，保存"修复前失败"的日志。
   如果契约与接口自相矛盾（例如要求完成后拉高 done，而模块根本没有完成输入），
   先报告矛盾，不要自行选一种解释再往下做。
2. 再改实现，直到用例通过，保存"修复后通过"的日志。
3. 改实现之前就建好报告的骨架，边做边填。不要留到最后，最后往往只剩总结的时间。

验收标准（我会逐条核对）：
- [ ] [可执行、可观察的判据 1]
- [ ] [判据 2]
- [ ] 修复前失败日志与修复后通过日志都在 [路径]
- [ ] 报告文件存在，且含"未验证项"一节。缺这一节视为未交付。

交付位置：实现放 [路径]，报告放 [路径]。
报告里必须写清：改了什么、为什么这么改、哪些没有验证、下一步建议。

完成后只回复：改动文件清单、测试命令与结果、未验证项。
```

## 变量说明

| 占位 | 填什么 | 填错的后果 |
| --- | --- | --- |
| 工作目录 | 绝对路径，含盘符 | agent 在别的目录建同名文件，构建到旧源码 |
| 只允许修改 | 尽量短，但必须包含契约文档、自查脚本、日志目录 | agent 顺手重构，或产出无处安放 |
| 先读这些 | 3 到 5 个文件，每个写理由 | agent 按文件名猜结构，例如按 YOLO 名称猜输出维度 |
| 接口契约 | 偏移、位宽、读写属性、错误语义 | 主机侧与硬件侧各写一套，联调时对不上 |
| 完成顺序 | 先红后绿 | agent 直接写实现，再用实现反推测试，测试等于没写 |
| 验收标准 | 能跑的命令或能看的文件 | 收到一段"已完成"但无法验证的回复 |

## 验收标准怎么判断 agent 真的做到了

按这四条核对，不满足就退回：

1. 它引用的文件路径真实存在，且它只改了白名单里的文件。
2. 失败日志的时间早于通过日志，两份日志的命令行一致。
3. 报告里出现"未验证"三个字。一份声称全部验证通过的回复通常意味着它没有验证。
4. 它没有把"工具跑完了"说成"结果正确"。

## 板卡不在手上时怎么改写

三条就够了：

- 白名单缩到契约文档与离线自查脚本，实现文件如果改不了就先不改。
- 验收标准里凡是要上板的项，改成"在指定路径写明 NOT_RUN 与原因"。
- 报告里"已离线验证"与"未验证"必须分两段，不允许合并成一句"已验证"。

## 计时类任务的验收标准怎么写

把一次调用拆成固定的五段，每段单独给数字，不给合计：

| 段 | 起点 | 终点 |
| --- | --- | --- |
| a | 数据搬入前 | 搬入完成 |
| b | 启动写寄存器 | 完成中断或状态位 |
| c | 结果可读 | 结果搬出完成 |
| d | 后处理开始 | 后处理结束 |
| e | 调用开始 | 返回 |

报告里同时给中位数与最小值，写清预热次数与样本数。目标改进幅度填在 [目标改进幅度：__ ms 或 __%]，
不要留空也不要现编。若某个探针会让中位耗时变化超过该幅度的三分之一，这次测量作废，换个测法再来。

## 常见失败

- 只说"实现 X 功能"：agent 会自己发明接口，然后主机侧与硬件侧对不上。
- 只给目录不给文件白名单：agent 会重构相邻模块，你无法判断回归来自哪里。
- 没写"先读哪些文件"：agent 从目录结构推断设计，猜错模型输入尺寸这类事就是这样发生的。
- 没写工具绝对路径：agent 找到另一份同名工具（例如另一个版本的 Vivado、另一个 Python），构建结果与你手上的报告不可比。
- 验收标准写成"功能正确"：这句话无法核对。写成"同一输入下 PL 输出与 FP32 参考逐元素差不超过 1 LSB，日志在 reports/numeric.log"。

## 已验证案例

同一套模板在该项目里用于派发传感器控制器改造、PYNQ 主机侧实现、只读复核三类任务。派发时把"只允许修改的文件"列成四项（camera_control.py、notebook、单元测试、结果文档），并明确"根目录拥有其它所有文件与构建"，子 agent 没有越界改动。

反例也来自同一项目：早期只写了"实现相机控制"而没写寄存器契约，子 agent 与硬件侧对同一个寄存器的位定义不一致，联调阶段才暴露，返工两轮。
