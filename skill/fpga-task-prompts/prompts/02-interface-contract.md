# 02 接口契约提示词

## 什么时候用

硬件侧（RTL 或 HLS 封装）与主机侧（PYNQ、C 驱动、测试脚本）由不同的人或不同的 agent 写，需要一个
双方都能引用的唯一契约时用这一条。典型信号：

- 有人问"这个寄存器的第 3 位到底什么意思"。
- 主机侧读回来的值一直是 0，或者恒为 0xFFFFFFFF。
- 同一个地址在 RTL 注释、HWH、Python 代码里出现三种写法。
- 写寄存器不报错，但行为没变。

## 提示词模板

```text
任务：为下面这个 IP 写一份接口契约，并让契约可从源码自动复核。

IP 名称：[名字]
基地址：[地址，或说明"从 HWH 读取，不写死"]
输入材料（都要读）：
1. RTL：[文件路径]，寄存器逻辑在哪几行
2. HWH 或 XSA：[路径]，用来核对偏移与位宽
3. 现有主机侧代码：[路径]，看它实际怎么用
4. 数据手册或既有约定：[路径或"无"]

输出一份契约文档，必须包含：

一、地址与访问属性表。每行一个寄存器，列固定为：偏移、名称、访问（RW/RO/WO/W1C/自清零）、
位域、复位值、含义、写错误时的总线行为。

一之补充。如果这个接口不是寄存器访问（AXI-Stream、串口帧、函数调用、文件格式），
上面那张表换成该形态自己的字段表，不能套寄存器模板：

| 接口形态 | 必须写清的字段 | 一个合法样本 | 判定非法的方式 |
| --- | --- | --- | --- |
| AXI-Stream | 位宽、字节序、tready/tvalid 规则、包首尾标记、背压时是否丢数 | 一帧的十六进制字节 | 断包、位宽不符、背压下丢数 |
| 串口/自定义帧 | 帧头、长度、命令字、载荷偏移与位宽、校验方式、空闲间隔、复位值 | 一条完整帧 | 校验错、长度不符、帧内超时 |
| 函数调用 | 签名、参数取值范围、返回值与错误码、是否可重入、超时后语义 | 一次调用的输入与期望返回 | 越界参数、重复调用、超时返回 |
| 文件/张量 | 形状、dtype、布局（NCHW/NHWC）、缩放与零点、对齐要求 | 一个文件的头几十字节 | 形状不符、dtype 不符、未量化 |

每一行都要给出"出处"（文件名加行号），没有出处的字段写 UNKNOWN 并列进待确认。

二、每个寄存器的语义，逐条写清：
- 写入什么时候生效（立即，还是下一个帧边界、下一次握手完成）。
- 读回值与实际生效值是否可能不同；如果不同，说明怎么读到实际生效值。
- 位宽大于 8 位、且由多个时钟域拼出来的字段，是否有原子读机制（快照、握手、Gray 码）。
- 保留位读回是什么，写非零会怎样。

三、错误与超时：
- 非法地址、非对齐访问、忙时提交，各自返回什么总线响应。
- 每个可能等待的操作，超时时间是多少、超时后主机侧该看到什么状态位。
- 硬件超时与软件超时谁更长，为什么。

四、一套可直接运行的只读自查步骤，按接口形态选：

- 寄存器接口：逐个寄存器读一次，把读回值与契约里的复位值对比，输出差异。
  若这个 IP 没有身份或版本寄存器，自查改为：写一个已知值再读回（只对 RW 寄存器）、复位值比对、
  以及不可写寄存器的写入无效性验证。
- 流/帧接口：发一条契约里的合法样本，比对接回的字节；再发一条故意改坏校验位的帧，确认被拒。
- 函数接口：调一次合法输入与一次越界输入，记录返回值与错误码。
- 文件/张量接口：读一个真实文件，断言形状、dtype、缩放系数与契约一致。

没有可用对照时，明确写"该接口无自动复核手段"，不要编造期望值。

五、一致性检查：把契约与现有接口逐条比对，列出矛盾项。例如契约要求"完成后给出 done"，
而模块端口里没有完成输入；或者契约写了只写寄存器，而主机侧代码在读它。
矛盾项单独成表，不要自行选一种解释圆过去，交给写契约的人决定。

要求：
- 契约里的每个数字都必须能在材料里找到出处，并在表格外加一列"出处"（文件名加行号）。
- 找不到出处的数字不要写，标成 UNKNOWN 并列进"待确认"。
- 不要按你的经验补默认值。

完成后回复：契约文件路径、UNKNOWN 项清单、以及你认为最可能与现有主机侧代码冲突的三条。
```

## 变量说明

| 占位 | 说明 |
| --- | --- |
| 基地址 | 宁可写"从 HWH 读"，也不要写死。写死的地址换一块板就错 |
| RTL 行号 | 让 agent 指出寄存器逻辑位置，便于你抽查 |
| 来源列 | 这是整份契约里最重要的一列，它把"约定"与"猜测"分开 |

## 验收标准

1. 表格里每个偏移都能在 RTL 或 HWH 里找到对应，没有凭空出现的寄存器。
2. 至少列出一个"读回值与实际生效值不同"的字段，并给出读实际值的方法。找不到时说明为什么不存在。
3. 有三处以上 UNKNOWN 是正常的，说明 agent 没有编数字。一处都没有反而要警惕。
4. 只读自查脚本在无板环境下能跑（读文件或读 HWH），或在有板环境能跑（逐个读寄存器）。

## 常见失败

- 契约里只写"该寄存器控制使能"，没写位序。另一位 agent 会按自己的习惯从 bit0 开始排。
- 把复位值当默认值。复位值只在配置后成立，运行时可能被别处改写。
- 忘记写"忙时提交返回 SLVERR"，主机侧于是把错误当成功，后面所有状态都对不上。
- 把多比特异步计数器当成普通只读寄存器，读回来的上下半拍来自不同时刻，数据看着合理但不对。

## 已验证案例

同一项目中，主机侧任务书里的寄存器表按上述结构写全（偏移、位域、读写属性、错误语义、40 秒硬件
超时对 45 秒软件超时），RTL 与 Python 两侧各自实现后一次联调通过。

反例：早期只给了"CONTROL 控制来源与使能"一句话，RTL 把来源放 bit0、使能放 bit1，Python 侧按
使能在 bit0 写了一个星期，表现为"设了使能没反应"。
