# 03 软硬划分提示词

## 什么时候用

手上有一个算法描述（论文、伪代码、Python 原型）和一块板，还没有决定哪一段放 PS、哪一段放 PL、
哪一段用 HLS、哪一段干脆留在软件里。这个阶段最容易出的问题是"先动手写 RTL，写到一半发现带宽不够"。

提示词的目的是让 agent 先交一份带数字的划分方案，而不是先交代码。

## 提示词模板

```text
任务：为一个算法做软硬划分，交付一份带数字的方案与一个最小验证切片。先不要写完整实现。

算法描述：
[贴伪代码或 Python 原型，说明输入输出形状、数据类型、每步的计算量]

目标平台：
- 器件：[型号或"由赛方提供的 PYNQ-Z2 / KV260 之一"]
- PS 侧：[ARM 核数、主频、可用内存]
- PL 侧可用资源：[DSP、BRAM、LUT 的粗略上限，或写"未知，需先综合一次空壳"]
- 连接：[HP 口数量与位宽、是否有 ACP、DMA IP 型号]
- 外部接口：[摄像头、HDMI、以太网，各自的分辨率与帧率]

性能目标：[例如"单帧端到端不超过 200 ms"，并说明这个目标是怎么来的]
精度目标：[例如"与 FP32 参考的检测框 IoU 不低于 0.95"，或"分类结果完全一致"]

请按这个顺序输出，每一步都要给数字：

第一步，算子清单。把算法拆成算子，逐个给：输入输出形状、数据类型、单次浮点运算量、
是否可并行、是否适合定点。

第二步，三类归属候选。对每个算子给出三种归属（PS 软件、PL 手写 RTL、PL HLS）各自的
预估耗时与资源占用，并说明依据（是实测、是同类设计经验、还是纯估算，必须标明）。
不允许只给一个推荐而不给另外两个的数字。

第三步，带宽与延迟账。按选定的划分，算出每一段要搬多少字节、总共搬几次、
按端口位宽与频率最多能搬多快。如果搬运时间超过计算时间，明确写出来。

第四步，接口与缓冲。给出每个边界上的接口类型（AXI4、AXI-Stream、共享内存加寄存器），
以及缓冲数量与所有权（谁分配、谁释放、什么时候可以复用）。

第五步，最小验证切片。选一条从输入到输出的最短路径，给出：
- 切片要验证的假设（例如"卷积部分放到 PL 后，单帧耗时降到 300 ms 以下"）
- 用固定输入（可复现的图样或固定图片）的对比方法
- 如果假设不成立，下一个要改的是什么

第六步，风险与回退。列出三个最可能让方案失效的原因，每个给出一个能在一天内做完的检测手段。

约束：
- 不要写完整 RTL 或完整 HLS，本阶段只交方案与切片。
- 任何估算都要标注置信度（实测、同类经验、纯猜）。
- 资源上限未知时，先给一个空壳工程的综合结果作为基线，不要用"应该够用"。
```

## 变量说明

| 占位 | 说明 |
| --- | --- |
| 算法描述 | 越具体越好。只给"一个 YOLO"会让 agent 自己选版本，后续所有数字都不可比 |
| 资源上限 | 未知就写未知，让 agent 先综合空壳。写一个假数字会污染整份账 |
| 性能目标 | 必须带来源。没有来源的目标会在优化阶段被反复改写 |
| 精度目标 | 决定定点位宽与是否需要逐层对比 |

## 验收标准

1. 三步之内出现具体数字，且每个数字标注了来源类别。
2. 带宽账里能看出"搬运时间与计算时间"的比较，而不是只有总时间。
3. 最小验证切片真的能在一两天内做完，不是"先做完整系统再验证"。
4. 方案里至少有一处写"这里我不确定，需要先测"。

## 常见失败

- agent 直接开始写 HLS：跳过账，做到一半发现 DDR 带宽是瓶颈。
- 只给推荐方案：没有另外两个归属的数字，你无法判断推荐是不是拍脑袋。
- 用"应该够用""通常可以"代替资源核算：这类句子出现在报告里就是风险点。
- 精度目标写成"尽量高"：定点位宽无从决定。

## 已验证案例

该项目早期把"摄像头采集加显示加推理"整条链一次做完，结果是帧率问题排查用掉两个版本周期。
后期改用先做最小切片（同一固定图从 DDR 进、出结果、不接摄像头不接显示）的做法，把模型移植
与数值验证从整机里剥出来，才把"模型错"与"显示错"分开。
