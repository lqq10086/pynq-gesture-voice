# 04 报告定位瓶颈提示词

## 什么时候用

综合或实现跑完了，手上有资源报告与时序报告，需要判断"下一步改哪里最划算"。或者性能不达标，
需要从报告与实测数据里找出真正的瓶颈，而不是凭印象优化。

触发信号：

- 报告里 WNS 为负或只有几十 ps，不知道是逻辑太深还是约束错了。
- 资源占用不高，但频率上不去。
- 主机侧测出的耗时与预估差很远。
- 有人提议"加并行度"或"提高时钟"，但说不清能换到多少。

## 提示词模板

```text
任务：从给定的报告与实测数据里定位瓶颈，输出一张按性价比排序的候选清单。不要改代码。

可用材料（都要读，读不到的明确说读不到）：
1. 综合报告：[路径]
2. 实现报告：[路径]，含时序汇总与资源占用
3. 布线后时序：[路径]，说明是否 post-route
4. 实测数据：[路径]，含测量边界说明
5. 当前设计规格：[文件路径]，含目标频率、时钟定义、器件型号
6. 工具版本：[例如 Vivado 2023.1，或写"未知"]

输出四段：

第一段，事实。只写报告里能直接读到的东西：目标时钟与频率、WNS/TNS/WHS、失败端点数量与所在时钟域、
LUT/FF/BRAM/DSP 占用率、有没有未约束路径。这一段不允许出现"因为所以"。

第二段，瓶颈假设。按证据强弱排序，最多五条。每条写：
- 假设内容
- 支持它的数字（引用报告里的具体行或表格）
- 能证伪它的一个检查（一条命令或一个报告字段）

第三段，候选优化。每条候选必须填五列：
前提（什么条件成立才有收益）、成本（资源、工期、构建次数）、
风险（可能让什么变差）、验证方法（在哪个边界上测什么）、回退方式（不成立时怎么退回）。
按"收益除以成本"排序，不按实现难度排序。

第四段，不该做的。列出三条看起来能优化、但实际上不该动的方向，并说明理由。

硬性要求：
- 任何"预计提升"都必须写清是估算还是实测。估算不超过一个区间，不给单点数字。
- 不允许把工具微基准的收益写成整机收益。
- 报告里出现的每个数字都要能指回源文件与行。
- 资源与频率的取舍，判断标准是目标器件上可测量的性能，不是占用率下降本身。
```

## 变量说明

| 占位 | 说明 |
| --- | --- |
| 实现报告 | 必须是 routed 之后的。只有 synth 报告时，先让 agent 说明"不具备判定资格" |
| 实测数据 | 必须带边界。没有边界的数据只能当参考 |
| 工具版本 | 版本不同，报告格式与默认策略不同，不能混着比 |

## 验收标准

1. 第一段没有因果词。出现"因为"就说明它在猜。
2. 每条假设都能被一条命令证伪。不能证伪的假设删掉。
3. 候选清单里有"不该做的"，且理由具体到资源或器件限制。
4. 收益全部带区间或边界，没有孤零零的"提升 30%"。

## 常见失败

- agent 只看资源占用就建议"减少 LUT"。资源不紧张时，减少 LUT 换不到频率。
- 把负裕量归因于"逻辑太深"，但实际是时钟没定义或 IO delay 缺失。
- 建议提高并行度，但没算 DDR 带宽，结果并行度上去了，端到端没变。
- 把一次综合的差异当成优化效果，而那次构建的器件或工具版本也变了。

## 已验证案例

该项目一次只读审计里，按上述四段写法产出 5 条候选，每条都带前提、成本、风险、验证与回退。
实施后按 A/B/C 控制变量复测，其中一条在固定输入端到端从 605.487 ms 降到 455.496 ms，中位减少
24.77%。同一份清单里另有一条更高并行度候选因布线后时序为负（WNS 负 0.637 ns）被放弃，保留为
失败记录，没有被删掉。

反例：早期把"历史某版本的 281 ms"当成当前模型性能，实际那是旧模型的完整链路计时，两个数字
不可相减。这类错误在第二段"支持它的数字"这一列会被直接暴露。
