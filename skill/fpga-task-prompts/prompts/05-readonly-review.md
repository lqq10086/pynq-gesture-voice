# 05 只读复核提示词

## 什么时候用

有一份设计、代码或报告需要第二个人看一眼，但你不想让它顺手改东西时用这一条。典型场景：

- 子 agent 刚写完一段 RTL 或主机侧代码，需要独立复核而不是自评。
- 要判断某个"已完成"的结论是否站得住。
- 交付前做最后一轮检查，需要一个只读视角。

这条提示词的关键是缩小权限、固定结论格式、强制写出"没有覆盖什么"。

## 提示词模板

```text
任务：只读复核。你只能读文件，只能新建一份报告文件，不得修改任何既有文件、不得运行综合、
实现、上板或烧写。如果发现必须运行才能判断的问题，写进"证据缺口"，不要自行运行。

复核范围（逐项列出，范围之外不评论）：
1. [文件或目录，以及要复核的关注点]
2. [同上]
3. [需要对照的契约或需求文档]

请读的材料：
- [设计文件、RTL、脚本]
- [对应的测试或日志]
- [契约文档：寄存器表、接口定义、验收标准]

输出结构固定为五节：

一、结论。分两行，每行一个词加一句话：
规格复核：PASS 或 FAIL，一句话说明依据。
质量复核：PASS 或 FAIL，一句话说明依据。
若证据不足以下结论，写 INSUFFICIENT，并说明缺什么。

二、逐条发现。每条固定四行：
- 位置：[文件路径:行号]
- 现象：[看到什么，不要写"可能有问题"]
- 影响：[会导致什么具体后果，例如"总线复位后旧响应被新命令消费"]
- 依据：[引用测试日志或代码行，说明这是已修复、遗留、还是不适用]

三、已核对但没有问题的项。列三到八条，每条一行，说明你核对了什么。
这一节的作用是让读者知道你的覆盖面，而不是只看问题。

四、证据缺口。写清：
- 本次复核没有运行什么（仿真、综合、实现、上板）。
- 因此哪些结论只是源码推断。
- 哪些结论必须由别人用另一份证据确认（例如布线后时序、板端实测）。

五、建议的下一步验证。最多三条，每条一句话，且必须是可以直接执行的动作。

要求：
- 不允许出现"基本可用""问题不大"这类无法核对的判断。
- 不允许改写被复核的文件，即使只有一行。
- 每条发现必须有文件路径与行号，没有行号的发现视为未完成。
- 你没读过的文件不要出现在结论依据里。
```

## 变量说明

| 占位 | 说明 |
| --- | --- |
| 复核范围 | 必须写死。不写死时 agent 会顺手评价整个工程 |
| 契约文档 | 没有契约时，复核只能评价"代码自洽"，价值有限 |
| 只读约束 | 要写两次：开头一次，要求里一次。只写一次常被忽略 |

## 验收标准

1. 结论只有 PASS、FAIL、INSUFFICIENT 三种，没有第四种措辞。
2. 每条发现都带文件和行号，抽查两条能对上。
3. 第四节非空。一份声称覆盖全部证据的复核报告，可信度低于一份老实列出缺口的报告。
4. 报告里没有出现它不该看的文件。

## 常见失败

- 没写"不得运行"，agent 自己跑了一次综合，报告里混进了新构建的结果，与你手上的报告不可比。
- 没要求写"已核对项"，你无法知道它到底看了多少，可能只看了目录。
- 没要求行号，发现无法定位，等于一条情绪。
- 结论写了"通过但有小问题"，读者无法判断能不能部署。

## 已验证案例

同一项目里，传感器控制、AXI 控制面、跨时钟域分别做过一次只读复核。复核报告的结构是：结论两行、
逐条发现带文件行号（例如某个复位问题指向某行），以及一节"证据缺口"，明确写"本次复核未运行仿真、
综合、实现与上板，布线后时序需另行确认"。

这份"证据缺口"后来起了作用：同一条链路的另一个候选实现仿真通过但布线后时序为负，正因为复核
报告没有声称覆盖时序，团队没有把"复核通过"当成"可以部署"。
