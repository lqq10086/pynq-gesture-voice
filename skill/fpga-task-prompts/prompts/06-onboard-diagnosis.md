# 06 板端异常分层定位提示词

## 什么时候用

板子上出现现象，但说不清是哪一层的问题时用这一条。典型现象：

- 画面花屏、错位、半帧、整帧重复。
- 寄存器读回是 0 或恒定值，写进去没反应。
- 帧率计数在涨，但看到的东西不变。
- 同一份代码昨天正常，今天不正常。
- 加了诊断之后变慢，不知道是链路问题还是诊断本身的开销。

这条提示词的作用是阻止 agent 直接跳到"改算法"或"调阈值"，先要求它把层分开。

## 提示词模板

```text
任务：定位下面的现象属于哪一层。先不要改任何功能代码，只允许加只读探针。

现象：[逐条写看到什么，出现频率，什么时候开始]
已尝试：[写过什么，改过什么，结果如何]
环境：板卡型号 [型号]，镜像与 overlay [版本]，工具版本 [版本]，采集与显示链路 [连接方式]
可用的只读观测手段：[计数器、日志、探针、示波器、另一台机器的抓包]

请按这个顺序做，每一步给出结论后再进下一步：

第一步，把"现象"翻译成计数。
列出这条链路上所有的帧率或事件计数，逐个写清定义（谁统计、统计什么、起止边界）。
至少要区分：传感器出帧、PL 完整帧、DMA 写完成、软件消费、算法推理、显示刷新。
一个问题里出现两个"帧率"就说明还没定义清楚。

第二步，控制变量实验。
保持输入、运行场景、预热方式、采样时长和其他负载一致，分别记录全开、仅关算法、仅关界面三组；
全关算法和界面可作为额外的组合对照。各组使用相同的计数定义与时间窗口。
关掉下游后上游计数不变，只能说明该对照中未观察到上游计数变化，不能单独确定瓶颈位置。

第三步，证明观测本身无害。
若加了新探针，用三档对照（关闭、轻量、详细）分别测一次。
若详细档让指标变化超过目标幅度的三分之一，该档数据作废，只用轻量档。

第四步，逐层判定。
对每一层写"通过、失败、未知"，并给出证据：
描述符与长度、所有权与缓存、搬运完成、帧边界与顺序、算法输入、算法输出、显示。
禁止把多层合并成一句"链路有问题"。

第五步，给出唯一的下一个实验。
只能给一个。写清：改什么、预期看到什么、如果没看到说明什么。

约束：
- 不要用"偶发""玄学""应该是缓存"当结论。
- 读回值不等于生效值。要用时间上靠后的可观测输出确认。
- 多比特计数器跨时钟读一次不算快照，读到拼接值时要说明。
- 任何"重启就好"的现象都记下来，它通常指向所有权或缓存。

完成后回复：五步的结论、下一实验、以及哪些结论只是推断。
```

## 变量说明

| 占位 | 说明 |
| --- | --- |
| 现象 | 要写频率与时序。写"有时候花屏"会导致第一步就分不清层 |
| 可用观测手段 | 决定实验可行性。没有额外仪器时，只能靠寄存器与日志 |
| 环境 | 板卡与 overlay 版本决定历史数据能不能引用 |

## 验收标准

1. 第一步列出了至少四个不同定义的计数。
2. 第三步真的做了三档对照，或者说明为什么不需要。
3. 第四步的层表按各层证据填写；证据不足的项标为"未知"。
4. 第五步只给一个实验，且带"如果没看到说明什么"。

## 常见失败

- agent 直接把"帧率低"归因于算法慢，但关掉算法后帧率不变。
- agent 加了整图比较的探针，单帧多花几十毫秒，然后用被探针拖慢的数据下结论。
- agent 用"读回成功"证明"写入生效"，实际上该位在下一次提交才被采样。
- agent 一次改三个地方（缓冲数、阈值、分辨率），之后无法归因。

## 已验证案例

同一项目中，帧率长期停在约 15 Hz，四组对照显示关掉算法与界面后写通道仍为 14.999 Hz，
于是问题从"算法太慢"改判为"上游出帧受限"，排查方向随之改变。

另一次，诊断探针自身带来约 50 ms 单帧开销，导致帧率从 30 掉到 20 左右。按第三步作废了该档
数据，随后用冻结快照把写通道稳定计数到 29.64 Hz，才把"视频链路健康"与"交互验收"分开下结论。
