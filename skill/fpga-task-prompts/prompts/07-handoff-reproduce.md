# 07 交接与复现提示词

## 什么时候用

要把工程交给一个完全不知情的人或 agent，或者要写"复现说明"这一节报告时用这一条。典型场景：

- 队友换人，新接手的人只有仓库，没有上下文。
- 比赛要提交"可由他人从零复现"的说明。
- 过了一个月自己回来做，忘记当时为什么这么改。

## 提示词模板

```text
任务：把这个版本整理成一份可交接的包，并写一份复现说明。不要改功能代码。

工程根目录：[绝对路径]
目标读者：[完全没参与过的队员、评委、或者三个月后的自己]
可用时间：[读者从零到看到结果能花多少小时]

第一步，资产清单与身份。
列出交付必需的文件：源码、约束、构建脚本、bit 与 HWH、模型与量化参数、板上脚本、数据。
每个关键产物给出哈希或版本号。区分三类：手写源码、生成物、外部下载。
逐项写明"这是必需还是可选"，以及"没有它会导致什么失败"。

第二步，证据分层。
把结论按证据强弱分层，每一层单独写，不要混：
- 软仿或单元测试通过
- C/RTL 或时序仿真通过
- 综合通过
- 实现通过且布线后时序为正
- 板端跑通（说明输入是什么、看到什么）
- 人看到效果（说明观察方式）
任何一层没有做，写 NOT_RUN 并说明原因。不要用"应该可以"填空。

第三步，复现步骤。
从一台干净机器开始写，顺序为：装环境、取代码、构建、部署、跑固定输入、核对输出。
每一步写：命令、预期输出、常见失败与对应处理。
命令必须是可以直接粘贴的，不要写"配置好环境后运行"。

第四步，不可复现的部分。
明确列出哪些结果无法由别人复现，及其原因（历史硬件已改、特定板卡、特定光照、需要未公开数据）。
这些不要删掉，也不要包装成"可选"。

第五步，交接时需要口头说清的三件事。
写三条最容易被忽略、但最容易让人踩坑的事实。例如某个脚本必须在特定目录下运行、
某个寄存器地址随 HWH 变化、某个现象是已知限制而不是缺陷。

约束：
- 断言"可复现"之前，必须自己按第三步在另一个目录完整走一遍。
- 不要把"我本地能跑"当作可复现。
- 目录名与文件名一律小写英文，正文中文。中文不要出现在路径里。
```

## 变量说明

| 占位 | 说明 |
| --- | --- |
| 目标读者 | 决定步骤粗细。写给评委时，每一步都要有预期输出 |
| 可用时间 | 超过四小时的流程需要标注"最小可验证子集" |
| 证据分层 | 这是整份交接里最有价值的一节，它防止把仿真结论当板端结论 |

## 验收标准

1. 资产清单区分了手写源码、生成物、外部下载三类。
2. 每一层证据都有"做了"或"NOT_RUN"的明确状态。
3. 第三步的每条命令都能直接粘贴执行，且带预期输出。
4. 第四步非空。没有不可复现部分的交接，通常是没写清楚。

## 常见失败

- 只写"运行 build.sh 即可"，但 build.sh 里是绝对路径，换机器就失败。
- 把 bit 与 HWH 当成一对，实际生成的 HWH 来自另一次构建，寄存器偏移对不上。
- 证据分层写成一段话："仿真和上板都通过了"，读者无法判断哪一层是推断。
- 把"队友的板子上见过效果"写成本项目已验证，实际没有留下日志或截图。

## 已验证案例

同一项目在多次版本交接中形成固定做法：每个版本目录里放一份构建与上板说明、一份证据清单，
并把无法复现的部分（例如某次特定光照下的白平衡、某块板子的 Flash 备份）单独列出并标为
NOT_RUN。交接包中保留失败候选与未采用方案，接手的人因此不会重复走同一条死路。

## 与其它模板的关系

第二步的证据分层直接决定报告里"功能正确性"与"可复现性"两节怎么写。第四步的内容通常就是
报告里最容易被扣分的地方，写清楚比藏起来安全。
